# Безопасность VOIDTWEAKS

Документ описывает модель защиты, порядок сообщения об уязвимостях и
требования к продакшен-окружению. Технические детали аудита — в
[`SECURITY_AUDIT_2026-11.md`](SECURITY_AUDIT_2026-11.md), модель угроз — в
[`THREAT_MODEL.md`](THREAT_MODEL.md), чек-лист выкладки — в
[`SECURITY_CHECKLIST.md`](SECURITY_CHECKLIST.md).

## Что защищаем

- лицензионные ключи и привязку ключа к аккаунту и ПК (HWID);
- аккаунты Supabase Auth (email + пароль);
- платежи ЮKassa и статусы заказов;
- админ-панель: чужие аккаунты, ключи, заказы и статистику;
- целостность установщика Windows-приложения.

## Сообщить об уязвимости

Не открывайте публичный issue с деталями эксплуатации. Напишите владельцу
проекта в GitHub (`voidtweaksapp`) или через приватный канал поддержки.
Укажите версию, шаги воспроизведения и ожидаемое/фактическое поведение.
Не тестируйте на чужих аккаунтах, не создавайте нагрузку и не выводите
данные других пользователей.

## Требования к окружению

- `SUPABASE_KEY` на Render — **secret/service_role**, не publishable.
  Публичный ключ не должен иметь доступа к таблицам `licenses` и
  `web_orders`: RLS включён, политики удалены, `anon`/`authenticated`
  лишены прав.
- `ADMIN_EMAILS` — список email администраторов через запятую. Проверка
  выполняется только на сервере; фронтенд не содержит email админа.
- `YUKASSA_SECRET_KEY`, `SUPABASE_KEY` и прочие секреты хранятся только
  в переменных окружения Render/Cloudflare, не в git и не в браузере.
- Публичный `sb_publishable_...` в `docs/*.html` — не секрет, его роль
  ограничена Auth. Доступ к данным идёт через backend.
- Сайт и API работают только по HTTPS.

## Границы доверия

1. Браузер → Cloudflare Worker: разрешены только известные Origin и
   маршруты API; Worker передаёт реальный IP клиента для rate-limit.
2. Worker → Render: Render не должен быть доступен в обход проверок
   дольше, чем необходимо; все решения об авторизации принимает Render.
3. Render → Supabase: service_role используется только на сервере,
   никогда не попадает в ответы и логи.
4. Windows-приложение → Render: только HTTPS, проверка ответа лицензии.
5. Обновления → GitHub Releases: HTTPS, allowlist домена, обязательный
   SHA-256 и лимит размера установщика.

## Остаточные риски

- GitHub Pages не позволяет задавать HTTP-заголовки; CSP и
  Referrer-Policy заданы meta-тегами, `frame-ancestors`/X-Frame-Options
  на уровне заголовков недоступны. Кликджекинг частично закрыт
  `X-Frame-Options` только на API.
- Rate-limit хранится в памяти процесса Render: после рестарта и при
  нескольких инстансах счётчики сбрасываются/не общие. Прямой запрос к
  Render может подставить свой `X-Forwarded-For`; через Worker заголовок
  перезаписывается реальным IP.
- Один аккаунт может создать несколько платежей; ограничение — по
  пользователю и IP, без глобального лимита.
- CSP вынужденно разрешает `'unsafe-inline'` для скриптов: страницы
  содержат встроенный JS. Это снижает защиту от XSS по сравнению с
  nonce/hash.
- Кэш ключей в `sessionStorage` живёт до 10 минут и очищается при
  выходе/потере сессии; данные админки не кэшируются.
- Админ-действия логируются, но неизменяемого аудита (WORM) нет.
- Подпись `.exe` сертификатом code signing не настроена; целостность
  обновления обеспечивается SHA-256 из GitHub Releases.
- Офлайн-токен лицензии в Windows-приложении подписан статическим
  ключом внутри клиента и может быть подделан локально. Это риск
  выручки, а не утечки серверных данных; для закрытия нужна
  асимметричная подпись и отдельные правки клиента.
