выложены** (ждём подтверждения владельца). Аудит выполнялся только на
своих сервисах и тестовых данных, без нагрузки и без доступа к чужим

Главный результат: **закрыт публичный доступ к таблицам `licenses` и

политик нет, RLS включён.

## Критическое

### C-1. Публичное чтение лицензий и заказов

- **Где:** Supabase, таблицы `licenses`, `web_orders`.
- **Суть:** publishable-ключ из `index.html` мог читать таблицы напрямую
  через PostgREST. Это раскрывало ключи, HWID, привязку к аккаунтам и
  идентификаторы платежей.
- **Исправление:** `supabase_lock.sql` — RLS, удаление политик,
  `revoke all on ... from anon, authenticated, public`.
- **Проверка:** `GET /rest/v1/licenses?select=*` и
  `/rest/v1/web_orders?select=*` с публичным ключом → **401**.
- **Остаточное:** убедиться, что Render использует service_role; иначе
  кабинет/оплата перестанут работать (см. чек-лист).

## Высокий

### H-1. Гостевой checkout и ключи без владельца

- **Суть:** можно было купить/получить ключ без аккаунта, ключ не был
  привязан к пользователю.
- **Исправление:** `/api/checkout` требует Supabase access_token; ключ
  пишется с `user_id`; claim проверяет владельца заказа/ключа.

### H-2. Админ-доступ доверял фронтенду

- **Суть:** email админа был зашит в `account.html`; панель показывалась
  по сравнению email на клиенте.
- **Исправление:** email удалён из фронтенда; панель включается только
  по `is_admin` с сервера; `/api/admin/*` проверяют токен и email, email
  должен быть подтверждён.

### H-3. Нет ограничений на перебор и флуд

- **Суть:** claim, checkout и license/check можно было вызывать без
  ограничений; за прокси все запросы выглядели с одного IP.
- **Исправление:** лимиты по IP и пользователю, `Retry-After`, очистка
  словарей; Worker передаёт реальный `CF-Connecting-IP` в
  `X-Forwarded-For`, перезаписывая клиентское значение.

### H-4. Токен заказа оставался в URL

- **Суть:** `?order=...` попадал в историю и Referer.
- **Исправление:** токен сразу сохраняется в localStorage и удаляется из
  адресной строки через `history.replaceState`; `Referrer-Policy:
  no-referrer`.

## Средний

- **M-1. Полные ключи в логах.** Логи Render писали ключ целиком.
  Исправлено: только префикс `XXXX-…`.
- **M-2. Нет security-заголовков у API.** Добавлены `nosniff`,
  `no-referrer`, `X-Frame-Options: DENY`, `Permissions-Policy`,
  `Cache-Control: no-store`; лимит тела 64 КБ.
- **M-3. Нет CSP/SRI на сайте.** Добавлены CSP и Referrer-Policy в
  `index.html`/`account.html`, SRI SHA-384 для `vendor/supabase.js`.
- **M-4. Кэш админки в `sessionStorage`.** Удалён; кэш ключей
  очищается при выходе и потере сессии.
- **M-5. Слабый минимум пароля.** Поднят с 6 до 8 символов в форме и
  сообщениях; рекомендуется продублировать в настройках Supabase Auth.
- **M-6. Worker пропускал любые методы/размеры и не проверял Origin.**
  Добавлены allowlist Origin, GET/HEAD/POST, лимит 16 КБ,
  security-заголовки, скрытие `Server`/`X-Powered-By`.
- **M-7. Нет аудита админ-действий.** Добавлена запись в лог: кто, что и
  с каким ключом сделал.

## Низкий

- **L-1. `target="_blank"` без `rel`.** Проверено: везде есть
  `rel="noopener"`.
- **L-2. `X-Frame-Options` для статики.** GitHub Pages не отдаёт
  заголовки; meta-вариант не поддерживается. Остаточный риск
  кликджекинга; для API заголовок есть.
- **L-3. Нет `security.txt`.** Добавлен `docs/.well-known/security.txt`.
- **L-4. Нет подписи `.exe`.** Целостность обновления держится на
  SHA-256 из GitHub Releases; сертификат code signing — задача владельца.

## Windows-приложение

- Лицензия проверяется по HTTPS на `/api/license/check`; ключ Supabase в
  клиенте не найден. Это главное — раньше клиент мог читать всю таблицу.
- Обновления: HTTPS, allowlist GitHub-релиза, обязательный SHA-256,
  лимит размера и повторная проверка хэша перед запуском.
- **Остаточный риск (средний):** офлайн-токен лицензии подписывается
  статическим ключом, зашитым в приложение (`LicenseManager`), а
  `license.dat` обфусцирован XOR. Локальный злоумышленник может
  подделать офлайн-токен. Это вопрос защиты выручки, а не утечки данных;
  для полноценного закрытия нужна асимметричная подпись (приватный ключ
  на сервере, публичный в приложении) и отдельное согласование правок
  клиента.
- Подпись установщика сертификатом code signing не настроена; параметры
  обновления при этом проверяются.

## Что осталось владельцу

1. Подтвердить, что в Render `SUPABASE_KEY` — service_role.
2. Включить 2FA на GitHub/Supabase/Render/Cloudflare.
3. Включить подтверждение email и минимум 8 символов в Supabase Auth.
4. Подписать установщик сертификатом code signing.
5. Выложить изменения после проверки: backend → frontend → Worker.
